## Reproduced blockers

All four cases below ran successfully against isolated localhost Supabase/PostgreSQL using synthetic company-owned fixtures. `node scripts/construction-scheduling-review.mjs` exits 1 when it reproduces the vulnerabilities. It is a diagnostic reproducer, not a passing acceptance suite. It preserves its synthetic evidence, including the deliberately cyclic graph, in that isolated database only.

1. **P1 — lost assignment through stale composite edit.** `schedule_assignments` grants authenticated INSERT/DELETE (migration line 76). A direct same-company insert does not advance the parent activity revision. Opening revision 1, inserting an assignment directly, then submitting the original revision 1 with an empty assignment list succeeds and deletes the new assignment. The RPC's expected revision check protects RPC-vs-RPC edits, not every supported write path. Direct dependency edits have the same missing invalidation. Close the write boundary or make every related mutation participate in locking/revision checks before release.
2. **P1 — false save confirmation through forged receipt.** Authenticated users can insert `schedule_requests` (line 78). The receipt guard checks company/actor, identity and current revision, but not that the supplied payload was ever persisted. Inserting a receipt for an existing own-company row with a different name, then calling the RPC with that request/payload, returns success at `return prior.result` without saving the name. This is an own-tenant integrity defect, not demonstrated cross-tenant access. Receipts must be server/database-generated evidence of the transaction, not client-writable assertions.
3. **P1 — concurrent dependency cycle.** Existing dependency trigger checks cycles per statement, while only RPC calls acquire the company advisory lock. Two authenticated SQL transactions (same privileges/identity as the API) inserted A→B and B→A before either committed; both committed. A graph cycle breaks dependency integrity and future Gantt consumers. All dependency mutation paths must share serialization/consistent validation.
4. **P2 — inactive-resource validation bypass.** The RPC rejects inactive resources, but a direct authenticated assignment insert succeeds for a deactivated own-company resource. Active-resource validation must also cover the direct API boundary or that boundary must be removed.

These require a coherent database write-boundary change, not an application-only guard. Do not simply revoke underlying table privileges while retaining SECURITY INVOKER: that also breaks the RPC. Do not turn the RPC into a postgres-owned SECURITY DEFINER shortcut. A narrowly privileged, RLS-bound writer design or equivalent comprehensive database guards needs implementation, threat review, and isolated acceptance. This review stops that affected architectural operation at the confirmed data-integrity blocker rather than publishing an unverified privilege change. No production migration was changed or applied.

## Architecture and remaining acceptance

Stable activity/resource IDs, company/project keys, structured dates/times, many-to-many assignments, task links and predecessor edges are an appropriate extensible foundation. Append-only snapshots retain revisions after adoption. Future Gantt views can consume these entities without replacing the core model, once graph integrity is fixed. Dependency type/lag, explicit immutable baselines, actual start/finish/attendance evidence, labor/time entries and cost-code links remain additive work; current audit timestamps and expected worker counts are not actual labor or completion metrics. Do not compute trustworthy analytics from inferred attendance or invalid graphs.

Scale risks remain: full company reads and pairwise overlap detection, no stable snapshot across independently paginated tables, and unpaginated task/project option lists. A task beyond the API row limit is absent from new-selection options; this review fixes preservation of an existing omitted link so an unrelated edit cannot silently clear it. Add targeted pagination/retention tests before claiming large-portfolio support. History UI's latest-100-event window may exclude every event for an older activity; label or load activity-specific history when needed. Company-wide lock serializes unrelated resource/job RPC writes: acceptable conservative start for small pilots, but measure contention before expansion.

Acceptance still needed after hardening: direct API relationship edits vs stale RPC; same-tenant receipt forgery; concurrent opposing dependency writes; inactive direct assignments; multi-page read/edit preservation and task options; clean baseline+Sprint 3+Sprint 4 migration replay; full desktop/mobile save/recovery rerun on the hardened build. Add these to the regular automated gate rather than relying only on this diagnostic.

Release Sprint 3 first, retarget PR #4 to main, then repeat schema/compatibility preflight. Production backup/restore verification and explicit release authorization remain prerequisites.
